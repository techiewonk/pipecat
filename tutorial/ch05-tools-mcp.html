Tools & MCP: letting the agent do things

⏱ 45 minLevel: intermediateHigh value

Function calling turns a talker into a doer: the LLM asks to run a function, Pipecat runs your Python and feeds the result back. MCP extends this to tools hosted in a separate server.

Function calling

🎯 Concept

The LLM returns "call get_weather(location=…)" instead of prose. Pipecat runs the function and returns the result to the model, which then speaks a natural answer. The function's name, typed args, and docstring are the schema the model reads.

async def get_current_weather(params: FunctionCallParams, location: str, format: str):
    """Get the current weather.
    Args:
        location: The city and state, e.g. "San Francisco, CA".
        format: "celsius" or "fahrenheit".
    """                                                    # <- docstring IS the schema
    await params.result_callback({"conditions": "nice", "temperature": "75"})

@llm.event_handler("on_function_calls_started")            # speak while a slow tool runs
async def _(service, function_calls):
    await tts.queue_frame(TTSSpeakFrame("Let me check on that."))

context = LLMContext(tools=[get_current_weather])          # register the tool

🐍 Python note — write good docstrings

The model relies entirely on the name/args/docstring to decide when and how to call. Vague docstring = the tool never gets used.

Variants across providers: -async (await network + interim updates), -stream, -video, -direct (auto schema), -advanced-functionschema (explicit typed schema). Docs: Function Calling.

MCP — tools from a separate server

The Model Context Protocol lets your bot use tools hosted elsewhere (memory, filesystem, a SaaS API) over a standard protocol. Connect with MCPClient via stdio (local subprocess) or streamable HTTP (remote).

from mcp import StdioServerParameters
from pipecat.services.mcp_service import MCPClient

mcp = MCPClient(StdioServerParameters(command="...", args=[...]))  # launch/connect server
tools = await mcp.register_tools(llm)                              # its tools become the LLM's
context = LLMContext(tools=tools)

🐍 Python note — stdio vs HTTP

stdio runs the tool server as a child process (great for local tools); streamable HTTP points at a URL (great for shared/remote). Same client, different parameters.

▶️ Run it

uv run python getting-started/07-function-calling.py   # ask "weather in Paris?"
uv run python mcp/mcp-stdio.py                          # ask it to remember, then recall

🔨 Modify it

Add a third tool get_time(location). Make get_current_weather genuinely async with a real HTTP call (see function-calling-*-async.py). Point mcp-streamable-http.py at a different MCP server.

⚠️ Common errors

LLM never calls the tool → vague docstring or not passed to LLMContext(tools=[...]). Hang after a call → missing await params.result_callback(...). MCP "command not found" → the stdio server binary isn't installed.

✅ Checkpoint

Where does a tool's schema come from, and how does MCP differ?

From the function's name, typed params, and docstring. An MCP tool lives in a separate standardized server instead of your bot's file.
