Chapter 0 · Part A — Core

Foundations: the shared vocabulary

⏱ 25 minLevel: beginnerDo this first

Every other chapter builds on the words defined here. Learn them once and the whole framework — and all 380 examples — becomes readable.

What Pipecat is

Pipecat is an open-source Python framework for building voice and multimodal AI agents — programs you talk to that talk back, in real time. It connects AI services (speech-to-text, a language model, text-to-speech) and a network transport (how audio reaches the user), keeping the round-trip fast (typically 500–800 ms). Official intro: docs.pipecat.ai.

Frames & the pipeline

🎯 Concept

Everything moving through a Pipecat app is a frame — a small typed packet (a chunk of audio, transcribed text, an LLM token, or a control signal). Frames travel through a pipeline: an ordered list of processors, each of which handles frames and passes them on.

  🎤 you speak
     │  (audio frames)
     ▼
[transport.input] ─▶ [STT] ─▶ [user aggregator] ─▶ [LLM] ─▶ [TTS] ─▶ [transport.output] ─▶ 🔊 bot speaks
     audio           text        adds to context     reply    audio         playback

Docs: Pipeline & frame processing.

The seven words you need

TermWhat it is
FrameA typed data packet flowing through the app.
FrameProcessorA node that receives frames, optionally transforms them, and pushes them onward. Sits in the pipeline.
PipelineAn ordered list of processors; order defines data flow.
PipelineWorkerOne agent = one pipeline.
WorkerRunnerStarts and supervises one or many workers — this is what makes multi-agent (Chapter 11) possible.
BusThe shared channel workers use to talk to each other (in-memory, Redis, or PGMQ).
TransportHow the user connects (WebRTC, Daily, phone…); always the first and last processor.

The skeleton shared by all 380 files

Open any example and you'll see this shape. Memorize it and every file is readable:

transport_params = {                     # how the user can connect (chosen at launch)
    "webrtc": lambda: TransportParams(audio_in_enabled=True, audio_out_enabled=True),
    "daily":  lambda: DailyParams(audio_in_enabled=True, audio_out_enabled=True),
}

async def run_bot(transport, runner_args):
    stt = DeepgramSTTService(api_key=...)          # 1. build services
    llm = OpenAILLMService(api_key=...)
    tts = CartesiaTTSService(api_key=...)
    pipeline = Pipeline([transport.input(), stt, llm, tts, transport.output()])  # 2. wire them
    worker = PipelineWorker(pipeline)              # 3. one agent = one pipeline

    @transport.event_handler("on_client_connected")   # 4. react to events
    async def _(transport, client): ...

    runner = WorkerRunner()                        # 5. run & supervise workers
    await runner.add_workers(worker)
    await runner.run()

async def bot(runner_args):                        # entry point (also Pipecat Cloud)
    transport = await create_transport(runner_args, transport_params)
    await run_bot(transport, runner_args)

if __name__ == "__main__":
    from pipecat.runner.run import main
    main()

🐍 Python note — dict of lambdas

transport_params maps a name to a lambda (a tiny unnamed function). The params aren't built until the transport is chosen at launch, so unused ones cost nothing. lambda: X means "a function that returns X."

🐍 Python note — async def / await

Voice apps do many things at once (listening while speaking). async def marks a function that can pause at await points without freezing the program. You mostly just put await before calls that go over the network.

Transports connect the pipeline to the world

A transport is the first and last processor. transport.input() produces incoming audio/video frames; transport.output() consumes outgoing ones. You pick a transport at launch and the code stays the same. Docs: Transports.

  world ─▶ [transport.input()] ─▶ ...your processors... ─▶ [transport.output()] ─▶ world
           (mic / network in)                               (speaker / network out)

✅ Checkpoint

1. What is a "frame," and what is a "processor"?

A frame is a typed data packet (audio, text, image, or control signal). A processor is a node in the pipeline that receives frames, optionally changes them, and pushes them onward.

2. What is the difference between a PipelineWorker and the WorkerRunner?

A PipelineWorker is one agent running one pipeline. The WorkerRunner starts and supervises workers — one now, many later — which is how multi-agent systems are built.

3. Where does a transport appear in the pipeline, and why does that matter?

First (transport.input()) and last (transport.output()). It's the boundary between the outside world and your processing, so it's swappable without touching the middle of the pipeline.

Chapter 1 · Part A — Core

Turn-taking: knowing when to listen and when to speak

⏱ 45 minLevel: beginner → intermediate

The hardest part of natural conversation is detecting when the user has finished a thought, and gracefully handling interruptions and silence. This chapter covers the decision layer; the raw audio machinery it relies on (VAD engines, resamplers, filters) is detailed next in Chapter 2.

The concept

🎯 Turn-taking = end-of-turn detection

Pipecat decides "the user's turn ended" by combining up to three signals: VAD (voice-activity detection — is there speech or silence?), transcription signals from the STT service, and an optional turn-detection model ("smart turn") that predicts whether a pause is a real end-of-turn or just a thinking pause. Around that sit interruptions (user talks over the bot), idle detection (user goes quiet), and muting (ignore user audio at chosen times).

Docs: Speech Input & Turn Detection, Interruptions, Detecting Idle Users.

mic audio ─▶ VAD (speech?/silence?) ─┐
STT partials ────────────────────────┼─▶ end-of-turn decision ─▶ run the LLM
turn model (real pause vs. end?) ─────┘

Configuring turn detection

Turn behavior is configured on the user aggregator (the processor that collects user speech into the context). The minimal setup is just a VAD analyzer; adding a smart-turn model is one more strategy.

# Minimal: VAD only (used in getting-started/06)
user_aggregator, assistant_aggregator = LLMContextAggregatorPair(
    context,
    user_params=LLMUserAggregatorParams(vad_analyzer=SileroVADAnalyzer()),
)

# Add a model-based turn detector (from turn-management-smart-turn-local-coreml.py)
user_params=LLMUserAggregatorParams(
    user_turn_strategies=UserTurnStrategies(
        stop=[TurnAnalyzerUserTurnStopStrategy(
            turn_analyzer=LocalCoreMLSmartTurnAnalyzer(smart_turn_model_path=path)
        )]
    ),
    vad_analyzer=SileroVADAnalyzer(),
)

🐍 Python note — strategies as a list

UserTurnStrategies(stop=[...]) takes a list of stop conditions. VAD gives a fast baseline; the turn analyzer refines it. You compose behavior by adding strategy objects rather than writing detection logic yourself.

Handling silence (idle)

When the user goes quiet, you usually want to nudge them, then eventually end the call. The pattern keeps a retry counter and escalates.

class IdleHandler:
    def __init__(self):
        self._retry_count = 0                     # state persists between idle events

    async def handle_idle(self, aggregator):
        self._retry_count += 1
        if self._retry_count == 1:                # 1st: gentle nudge
            msg = {"role": "developer", "content": "The user has been quiet. Ask if they're still there."}
            await aggregator.push_frame(LLMMessagesAppendFrame([msg], run_llm=True))
        elif self._retry_count == 2:              # 2nd: firmer
            ...
        else:                                     # 3rd: say goodbye and end
            await aggregator.push_frame(TTSSpeakFrame("It seems you're busy. Have a nice day!"))
            await aggregator.push_frame(EndWorkerFrame())

🐍 Python note — run_llm=True

LLMMessagesAppendFrame([msg], run_llm=True) both injects a message and triggers a response, so the nudge is spoken immediately.

Muting (mic-off) — quick preview

You often want to ignore the user's mic at specific moments — while the bot is still delivering its first message, or while a function call runs — to prevent the bot interrupting itself or capturing stray audio. Pipecat calls these user-mute strategies. The full treatment (all strategies, events) is in Chapter 2 → Muting; the one-liner:

user_params=LLMUserAggregatorParams(
    user_mute_strategies=[
        MuteUntilFirstBotCompleteUserMuteStrategy(),   # ignore mic until the intro finishes
        FunctionCallUserMuteStrategy(),                # ignore mic while a tool runs
    ],
    vad_analyzer=SileroVADAnalyzer(),
)

VAD (speech vs. silence), STT transcription signals, and an optional turn-detection model.

2. Where is turn detection configured?

On the user aggregator, via LLMUserAggregatorParams (vad_analyzer and/or user_turn_strategies).

So the bot doesn't capture its own audio or treat leftover noise as the user interrupting before the intro finishes.

Chapter 2 · Part A — Core

Audio & Frame Processing — the production media stack

⏱ 70 minLevel: intermediateProduction-critical

This is the chapter that separates a demo from a shippable product. Every knob that touches raw audio — voice detection, resampling, noise removal, background beds, muting, DTMF, recording — plus the general-purpose frame-processing toolbox lives here, each explained once.

The audio signal chain

🎯 Where each piece sits

Incoming audio passes through an optional noise filter and resampler before VAD and STT. Outgoing audio can be blended with a mixer (background bed) before playback. Muting gates whether user audio is processed at all. These are configured on TransportParams and on the user aggregator — not by rewriting the pipeline.

IN :  mic ─▶ [audio_in_filter: noise cancel] ─▶ [resampler] ─▶ [VAD] ─▶ STT ─▶ ...
                         (muting can drop user audio here, before it's processed)
OUT:  ... TTS ─▶ [audio_out_mixer: background bed] ─▶ speaker
REC:  [AudioBufferProcessor] taps the stream to disk

2.1 Voice Activity Detection (VAD)

VAD answers "is this speech or silence?" — the fastest turn signal (Chapter 1 uses it). Pipecat ships several engines plus tunable parameters and a controller.

from pipecat.audio.vad.silero import SileroVADAnalyzer
from pipecat.audio.vad.vad_analyzer import VADParams

vad = SileroVADAnalyzer(params=VADParams(
    confidence=0.7,      # how sure before calling it "speech"
    start_secs=0.2,      # speech must persist this long to start a turn
    stop_secs=0.8,       # silence this long ends the turn
    min_volume=0.6,
))

AICQuailVADAnalyzerpipecat.audio.vad.aic_quail_vadai-coustics "Quail" model; see voice-aicoustics-vad-only.py.

2.2 Resampling (the "sampler")

Services and transports run at different sample rates (8 kHz phone audio vs. 16/24 kHz models). A resampler converts between them so nothing sounds chipmunked or clips. Usually automatic, but you can choose the engine for quality vs. speed.

from pipecat.audio.resamplers.soxr_resampler import SOXRAudioResampler
resampler = SOXRAudioResampler()          # high quality, batch
# streaming variant for realtime: SOXRStreamAudioResampler
# lightweight alternative:         ResampyResampler
ResamplerImportNotes

2.3 Noise cancellation filters

A noise filter cleans the incoming mic stream (removes background hum, keyboard, room noise) before VAD/STT — a big quality win for real calls. Attach one via audio_in_filter on the transport params.

from pipecat.audio.filters.krisp_viva_filter import KrispVivaFilter
# in transport_params:
"webrtc": lambda: TransportParams(
    audio_in_enabled=True,
    audio_out_enabled=True,
    audio_in_filter=KrispVivaFilter(),     # clean the mic before anything else
)

2.4 Background audio (mixers)

A mixer blends a sound file under the bot's speech — hold music, ambience, a "we're thinking" bed. Attach via audio_out_mixer, then control it live with frames.

from pipecat.audio.mixers.soundfile_mixer import SoundfileMixer
from pipecat.frames.frames import MixerEnableFrame, MixerUpdateSettingsFrame

"webrtc": lambda: TransportParams(
    audio_out_enabled=True,
    audio_out_mixer=SoundfileMixer(sound_files={"office": "assets/office-ambience.mp3"},
                                   default_sound="office", volume=0.3),
)
# later, at runtime:
await worker.queue_frame(MixerUpdateSettingsFrame({"volume": 0.5}))   # duck/boost
await worker.queue_frame(MixerEnableFrame(False))                     # turn bed off

Reference example: audio/audio-bot-background-sound.py.

2.5 Muting (mic-off) — server-side strategies

🎯 What "mute" means here

Rather than a client button, Pipecat mutes on the server: it drops user audio during moments where listening would cause bugs — while the greeting plays, or while a function call is running. You declare strategies and Pipecat applies them.

from pipecat.turns.user_mute import (
    MuteUntilFirstBotCompleteUserMuteStrategy,
    FunctionCallUserMuteStrategy,
)

user_params=LLMUserAggregatorParams(
    user_mute_strategies=[
        MuteUntilFirstBotCompleteUserMuteStrategy(),   # ignore mic until the intro finishes
        FunctionCallUserMuteStrategy(),                # ignore mic while a tool runs
    ],
    vad_analyzer=SileroVADAnalyzer(),
)

@user_aggregator.event_handler("on_user_mute_started")
async def _(aggregator): logger.info("mic muted")
@user_aggregator.event_handler("on_user_mute_stopped")
async def _(aggregator): logger.info("mic live")

🐍 Python note — declarative, not imperative

You don't write "if bot_speaking: drop_audio()". You add strategy objects to a list and subscribe to on_user_mute_started/stopped events for UI feedback. Reference: turn-management-user-mute-strategy.py.

2.6 DTMF & volume

On phone calls, DTMF is the keypad tones ("press 1 for sales"). Pipecat represents presses as KeypadEntry (pipecat.audio.dtmf) and can drive menus — see features/features-dtmf-menu.py. Output loudness is handled by pipecat.audio.volume.

2.7 Recording the conversation

Insert an AudioBufferProcessor (pipecat.processors.audio.audio_buffer_processor) to tap the audio stream and save it to disk without altering playback. Reference: audio/audio-recording.py.

2.8 The frame-processing toolbox

Beyond audio, Pipecat ships general-purpose processors you'll reuse constantly. A custom processor is just a class with one method:

from pipecat.processors.frame_processor import FrameProcessor

class TranscriptionLogger(FrameProcessor):
    async def process_frame(self, frame, direction):
        await super().process_frame(frame, direction)   # 1. always call super first
        if isinstance(frame, TranscriptionFrame):        # 2. react only to what you care about
            logger.info(f"User said: {frame.text}")
        await self.push_frame(frame, direction)          # 3. always forward the frame

🐍 Python note — the two mandatory calls

Every process_frame override must call super().process_frame(...) first and push_frame(...) to forward. Forgetting push_frame "swallows" frames and stalls the pipeline.

Chapter 3 · Part A — Core

Speech I/O: STT + TTS as swappable bricks

⏱ 30 minLevel: beginner

Speech-to-text (ears) and text-to-speech (voice) are interchangeable services in fixed pipeline slots. Learn the pattern once and every one of the 60+ providers is a one-line swap.

The concept

🎯 Drop-in services

Every STT provider subclasses STTService; every TTS provider subclasses TTSService. They occupy the same pipeline positions, so changing vendor = changing the imported class and its Settings. Nothing else moves.

audio ─▶ [ STTService ] ─▶ text ......... text ─▶ [ TTSService ] ─▶ audio
         Deepgram / AssemblyAI / ...            Cartesia / ElevenLabs / ...

Docs: Speech to Text, Text to Speech.

Swapping providers

stt = DeepgramSTTService(api_key=os.environ["DEEPGRAM_API_KEY"])
tts = CartesiaTTSService(api_key=os.environ["CARTESIA_API_KEY"],
    settings=CartesiaTTSService.Settings(voice="71a7ad14-...-01c121"))
# switch vendor: change the class + settings, keep the pipeline slot
# stt = AssemblyAISTTService(api_key=...)
# tts = ElevenLabsTTSService(api_key=..., settings=ElevenLabsTTSService.Settings(voice_id="..."))

🐍 Python note — HTTP vs streaming

-http variants (e.g. voice-cartesia-http.py) return audio in one response; the default streams it as generated (smoother, slightly lower latency). Same class family, different transport under the hood.

Changing voice / language at runtime

from pipecat.frames.frames import TTSUpdateSettingsFrame, STTUpdateSettingsFrame
await tts.queue_frame(TTSUpdateSettingsFrame({"voice": "<another-voice-id>"}))
await stt.queue_frame(STTUpdateSettingsFrame({"language": "es"}))

A settings change travels as a frame, so it stays ordered with the conversation. Full runtime-switching examples: the update-settings/ folder.

Brain & Memory: the LLM and its context

⏱ 40 minLevel: intermediate

The LLM is the reasoning core, but it's stateless — it only knows what you resend each turn. Pipecat manages that memory (the context), keeps it across sessions, and compresses it when it grows.

Context is the memory

🎯 Concept

An LLMContext is the running list of messages (system, user, assistant) sent to the model every turn. The context aggregator pair records both sides automatically. Swap models freely — each provider is an LLMService in the same slot.

user_aggregator ─▶ [ LLMContext: system, user, assistant, ... ] ◀─ assistant_aggregator
                              │ resent to the LLM every turn
                              ▼  (optional) summarizer collapses old turns

Docs: Context Management, LLM Inference.

Building & kicking off context

llm = OpenAILLMService(api_key=os.environ["OPENAI_API_KEY"],
    settings=OpenAILLMService.Settings(system_instruction="You are helpful and brief."))

context = LLMContext()
user_aggregator, assistant_aggregator = LLMContextAggregatorPair(
    context, user_params=LLMUserAggregatorParams(vad_analyzer=SileroVADAnalyzer()))

context.add_message({"role": "developer", "content": "Please introduce yourself."})
await worker.queue_frames([LLMRunFrame()])   # trigger a first response

🐍 Python note — messages are dicts

Each message is a dict with role and content. Roles: system/developer (instructions), user, assistant.

Runtime model settings

from pipecat.frames.frames import LLMUpdateSettingsFrame
await llm.queue_frame(LLMUpdateSettingsFrame({"temperature": 0.2}))

Persistence & summarization

Persistence keeps the context across reconnects/sessions (the persistent-context/ examples; realtime providers keep memory in-model). Summarization compresses old turns to stay under token limits and cost (context-summarization/). Docs: Context Summarization.

The LLM is stateless — it has no memory of prior turns, so the whole conversation is resent each time.

Tools & MCP: letting the agent do things

⏱ 45 minLevel: intermediateHigh value

Function calling turns a talker into a doer: the LLM asks to run a function, Pipecat runs your Python and feeds the result back. MCP extends this to tools hosted in a separate server.

Function calling

🎯 Concept

The LLM returns "call get_weather(location=…)" instead of prose. Pipecat runs the function and returns the result to the model, which then speaks a natural answer. The function's name, typed args, and docstring are the schema the model reads.

async def get_current_weather(params: FunctionCallParams, location: str, format: str):
    """Get the current weather.
    Args:
        location: The city and state, e.g. "San Francisco, CA".
        format: "celsius" or "fahrenheit".
    """                                                    # <- docstring IS the schema
    await params.result_callback({"conditions": "nice", "temperature": "75"})

@llm.event_handler("on_function_calls_started")            # speak while a slow tool runs
async def _(service, function_calls):
    await tts.queue_frame(TTSSpeakFrame("Let me check on that."))

context = LLMContext(tools=[get_current_weather])          # register the tool

🐍 Python note — write good docstrings

The model relies entirely on the name/args/docstring to decide when and how to call. Vague docstring = the tool never gets used.

Variants across providers: -async (await network + interim updates), -stream, -video, -direct (auto schema), -advanced-functionschema (explicit typed schema). Docs: Function Calling.

MCP — tools from a separate server

The Model Context Protocol lets your bot use tools hosted elsewhere (memory, filesystem, a SaaS API) over a standard protocol. Connect with MCPClient via stdio (local subprocess) or streamable HTTP (remote).

from mcp import StdioServerParameters
from pipecat.services.mcp_service import MCPClient

mcp = MCPClient(StdioServerParameters(command="...", args=[...]))  # launch/connect server
tools = await mcp.register_tools(llm)                              # its tools become the LLM's
context = LLMContext(tools=tools)

🐍 Python note — stdio vs HTTP

stdio runs the tool server as a child process (great for local tools); streamable HTTP points at a URL (great for shared/remote). Same client, different parameters.

▶️ Run it

uv run python getting-started/07-function-calling.py   # ask "weather in Paris?"
uv run python mcp/mcp-stdio.py                          # ask it to remember, then recall

🔨 Modify it

Add a third tool get_time(location). Make get_current_weather genuinely async with a real HTTP call (see function-calling-*-async.py). Point mcp-streamable-http.py at a different MCP server.

⚠️ Common errors

LLM never calls the tool → vague docstring or not passed to LLMContext(tools=[...]). Hang after a call → missing await params.result_callback(...). MCP "command not found" → the stdio server binary isn't installed.

✅ Checkpoint

Where does a tool's schema come from, and how does MCP differ?

From the function's name, typed params, and docstring. An MCP tool lives in a separate standardized server instead of your bot's file.

Gemini Live: realtime speech-to-speech

⏱ 60 minLevel: intermediateCapstone engine

Realtime models collapse STT + LLM + TTS into a single speech-to-speech service — lower latency, server-side turns. This is the engine our A2A capstone standardizes on.

One model instead of three

🎯 Concept

Instead of chaining STT → LLM → TTS, you send audio to Gemini Live and get audio back. Fewer swappable parts, but much lower latency, and the model manages turns itself. Other realtime engines: OpenAI Realtime, AWS Nova Sonic, Grok, Inworld, Ultravox.

[transport.input] ─▶ [ Gemini Live: speech-in ➜ think ➜ speech-out ] ─▶ [transport.output]
                       (one service replaces STT + LLM + TTS)

Gemini Live with tools + search

from pipecat.adapters.schemas.function_schema import FunctionSchema
from pipecat.adapters.schemas.tools_schema import AdapterType, ToolsSchema
from pipecat.services.google.gemini_live.llm import GeminiLiveLLMService

weather_function = FunctionSchema(
    name="get_current_weather", description="Get the current weather",
    properties={"location": {"type": "string", "description": "City, State"},
                "format": {"type": "string", "enum": ["celsius", "fahrenheit"]}},
    required=["location", "format"], handler=fetch_weather_from_api)

search_tool = {"google_search": {}}                       # Gemini-native tool
tools = ToolsSchema(standard_tools=[weather_function],
                    custom_tools={AdapterType.GEMINI: [search_tool]})

llm = GeminiLiveLLMService(
    api_key=os.environ["GOOGLE_API_KEY"],
    settings=GeminiLiveLLMService.Settings(
        system_instruction=system_instruction,
        voice="Aoede"),                                   # Puck, Charon, Kore, Fenrir, Aoede
    tools=tools)

🐍 Python note — explicit schemas

In Chapter 5 the docstring was the schema. Realtime providers want an explicit FunctionSchema (name, properties, required, handler), and provider-native tools go under custom_tools.

⚠️ Known quirk (from the example's own comment)

With GeminiVertexLiveLLMService you currently can't combine google_search with other tools — use the non-Vertex GeminiLiveLLMService for the combined setup.

🐍 Note — turns

Gemini Live drives turns server-side and does not emit UserStartedSpeaking/Stopped frames. Context aggregation still works; just don't rely on those frames for custom turn logic.

uv run python realtime/realtime-gemini-live.py    # needs GOOGLE_API_KEY

Flows: structured, reliable conversations

⏱ 60 minLevel: intermediate → advanced

For step-by-step tasks — intake, ordering, reservations, triage — a single free-form prompt is unreliable. Flows models the conversation as a graph of nodes, each with its own instructions and allowed tools.

Conversation as a graph

🎯 Concept

Each node has its own role/task messages and a scoped set of tools; a FlowManager moves between nodes as the user progresses. This keeps the bot on-task and dramatically more accurate than one giant prompt.

Docs: Pipecat Flows.

A node and a transition

def create_initial_node() -> NodeConfig:
    return NodeConfig(
        name="initial",
        role_messages=[{"role": "system", "content": "You are a friendly assistant."}],
        task_messages=[{"role": "system", "content": "Ask the user their favorite color."}],
        functions=[record_favorite_color])          # only this tool is allowed here

async def record_favorite_color(flow_manager, color: str) -> tuple[str, NodeConfig]:
    return "Thanks!", create_end_node()             # RETURN the next node to advance

🐍 Python note — return (result, next_node)

A flow function returns both what to say and which node comes next. That return value is how the graph advances — the core idea of Flows.

⚠️ Common errors

Conversation stuck → a flow function didn't return a next node. Bot goes off-script → tools not scoped to the node (functions=[...]).

✅ Checkpoint

What does a flow function return, and why?

A tuple of the spoken result and the next NodeConfig, so the graph advances.

Multi-agent A2A patterns

⏱ 2–3 hLevel: advancedCapstone prep

Everything so far was one agent. Pipecat is also a multi-agent system: one WorkerRunner coordinates many agents talking over a shared bus. A normal bot is just the one-agent case — so every app is already A2A-ready.

Agents on a bus

🎯 Concept

A worker is a unit of work on a shared message bus. The main worker owns the transport (STT/TTS) and bridges audio to the bus; specialist workers (each an LLMWorker with its own LLM + context) sit on the bus. The six patterns below are all built from this.

                    ┌──────────── shared bus ────────────┐
 [main PipelineWorker]        [LLMWorker: greeter]   [LLMWorker: support]
 STT/TTS + transport          (own LLM + context)    (own LLM + context)
 bridges audio to bus ── activate/deactivate = "who's talking now"

Docs: Agent Handoff, Job Coordination, Distributed Agents, Proxy Agents, UI Worker, The Worker Bus.

Pattern 1 — Handoff

Several LLM agents swap "who's talking" on one audio pipeline (greeter → support).

class AcmeLLMTask(LLMWorker):
    @tool                                              # a tool exposed to THIS agent's LLM
    async def transfer_to_agent(self, params, agent: str, reason: str):
        await self.activate_worker(agent,              # hand control to another agent…
            args=LLMWorkerActivationArgs(...),
            deactivate_self=True)                       # …and step aside

# in run_bot:
runner = WorkerRunner(handle_sigint=runner_args.handle_sigint)
main = PipelineWorker(pipeline, bus=runner.bus)        # main bridges transport <-> bus
await runner.add_workers(build_greeter(), build_support(), main)   # many agents, one runner
await runner.run()

🐍 Python note — handoff is activation, not a call

Agents don't call each other like functions. The greeter activates support and deactivates itself, flipping which agent owns the shared audio.

Pattern 2 — Parallel fan-out (job coordination)

One agent dispatches a job to several peers at once and synthesizes the results.

async def debate(params, topic: str):
    async with params.pipeline_worker.job_group(       # dispatch to several peers at once
        DebateWorker("advocate"), DebateWorker("critic"), DebateWorker("analyst"),
    ) as group:
        results = await group.run(topic)               # wait for all three
    # main agent then synthesizes `results` into one spoken answer

🐍 Python note — async with … as group

An async context manager sets up the job group and guarantees cleanup; await group.run(...) gathers every peer's result before continuing.

Patterns 3–6 — sidecar, distributed, proxy, UI

  • Sidecar: the main pipeline delegates to a long-lived peer via job(...) — a codebase agent (code-assistant/) or a hardware controller (sensor-controller/).
  • Distributed: the same handoff across processes/machines over a network bus — redis-handoff/ and pgmq-handoff/. Only bus= changes.
  • Proxy: two WebSocket proxies bridge a local transport to a remote LLM worker, no shared bus (remote-proxy-assistant/).
  • UI worker: an agent bridges the bus to a web client (snapshot, deixis "explain this", form-fill, async job progress) — the ui-worker/ examples.

▶️ Run it

cd examples/multi-worker && cp env.example .env
uv run python local-handoff/local-handoff-two-agents.py    # ask something only "support" handles
uv run python parallel-debate/parallel-debate.py           # give a topic, hear 3 views synthesized

🔨 Modify it

Add a third agent ("billing") to the handoff with a transfer_to_agent path. Add a fourth DebateWorker("historian"). Point the handoff at a RedisBus to split agents across processes.

⚠️ Common errors

Handoff silent → main worker isn't bridging to runner.bus, or no agent is active on connect. Job group hangs → a peer never returns. Redis/PGMQ fails → the bus service isn't running or its URL is unset.

✅ Checkpoint

1. What makes an app multi-agent?

More than one worker on the shared bus, coordinated by one WorkerRunner.

2. How does control move in handoff?

By activating another worker and deactivating the current one — not a function call.

3. What does job_group add?

Parallel dispatch to multiple peers and collection of all results before answering.

Capstone: an all-in-one Gemini Live A2A (local + distributed)

⏱ projectLevel: advanced

This ties the whole course together: a multi-agent, agent-to-agent system built on Gemini Live, using the A2A patterns, that runs both locally (in-memory bus) and distributed (Redis/PGMQ).

Target architecture

 user ──▶ [ MAIN PipelineWorker ]  owns transport + bridges audio to the bus
                  │
     ┌────────────┼─────────────────────────┐
     ▼            ▼                          ▼
[Gemini triage] [Gemini specialist A]  [Gemini specialist B]   ← handoff (who's talking)
     │
     └─ debate tool ─▶ job_group(advocate, critic, analyst)     ← parallel fan-out
 bus = InMemory (local)  ⇄  RedisBus / PgmqBus (distributed) — same agent code

Recommended build order

  1. One Gemini Live agent (Ch 6) — get realtime-gemini-live.py talking with one tool.
  2. Add a second agent + handoff (Ch 11) — wrap Gemini Live inside LLMWorkers and swap control with activate_worker.
  3. Add parallel fan-out (Ch 11) — a debate-style tool dispatching to several Gemini agents, then synthesize.
  4. Go distributed — switch the in-memory bus for RedisBus/PgmqBus; agents run in separate processes. Agent code is unchanged; only bus= changes.
  5. Optional UI worker — surface state to a web client.

The key wiring (annotated)

# Each specialist is a Gemini Live agent on the bus
class TriageAgent(LLMWorker):
    @tool
    async def route(self, params, department: str, reason: str):
        await self.activate_worker(department, deactivate_self=True)   # handoff

# main worker owns transport + audio, bridges to the bus
runner = WorkerRunner(handle_sigint=runner_args.handle_sigint)
main = PipelineWorker(pipeline_with_gemini_io, bus=runner.bus)
await runner.add_workers(TriageAgent("triage"), SpecialistA("billing"),
                         SpecialistB("support"), main)
await runner.run()

# distributed: same code, swap the bus
# runner = WorkerRunner(bus=RedisBus(url=os.environ["REDIS_URL"]))

⚠️ Gemini-specific gotchas

Gemini Live is speech-to-speech, so the main worker still owns the transport and bridges audio; each child is a Gemini Live LLM on the bus. Gemini drives turns server-side and emits no turn frames — don't build custom turn logic on those. And google_search can't combine with other tools on the Vertex variant (Ch 6).
