Lesson 1 · Part I — Principles

What Pipecat is

⏱ 20 minLevel: beginner

Before any code, build the right mental model. Pipecat is a real-time frame-processing engine with an AI-services layer and a multi-agent layer on top. Seven ideas hold the whole framework together — learn them and 567 source files become readable.

The definition

🎯 In one sentence

Pipecat orchestrates AI services (speech-to-text, LLMs, text-to-speech, vision…), network transports, and audio processing into ultra-low-latency pipelines so you can build voice and multimodal agents that feel natural — typically a 500–800 ms round trip.

The seven core ideas

1 · Everything is a Frame

frames/frames.py defines 125 frame classes under three bases that decide scheduling: SystemFrame (a high-priority lane — interruptions, input audio, errors, speaking events), and DataFrame / ControlFrame (an ordered lane — text, output audio, LLM/TTS boundaries). Media mix-ins (AudioRawFrame, ImageRawFrame, TextFrame) add payloads. This taxonomy is the framework's vocabulary.

2 · Everything is a FrameProcessor

One base class — process_frame(frame, direction) + push_frame(), chained by link(), moving frames DOWNSTREAM/UPSTREAM. A Pipeline is just an ordered list wrapped by a source/sink. Every service, transport, aggregator, and filter is a FrameProcessor:

3 · Services are FrameProcessors with a settings/streaming discipline

AIService → STTService / TTSService / LLMService / VisionService. The Settings pattern (services/settings.py) uses a dataclass in two modes — a complete "store" and a sparse "delta" (NOT_GIVEN) carried by *UpdateSettingsFrame. That single idea is how every runtime setting change works. Most LLM providers are thin subclasses of BaseOpenAILLMService.

4 · Turn-taking lives on the aggregator, not the transport

🔬 The thing old tutorials get wrong

The transport now only does audio/video I/O (+ an optional audio_in_filter and audio_out_mixer). VAD, turn detection, and muting are configured on the LLM user aggregator via LLMUserAggregatorParams(vad_analyzer=…, user_turn_strategies=…, user_mute_strategies=…). The default stop strategy is a smart-turn ML model (LocalSmartTurnAnalyzerV3) gated by VAD + transcript. We cover this in Lesson 10.

5 · Realtime collapses three services into one

A cascaded agent is STT → LLM → TTS. A realtime speech-to-speech service (Gemini Live, Nova Sonic…) is a single LLMService that consumes InputAudioRawFrame and emits TTSAudioRawFrame directly — lower latency, server-driven turns, fewer swappable parts (Lesson 15).

6 · Multi-agent is the same engine over a bus

A WorkerRunner owns a WorkerBus (in-memory / Redis / PGMQ) and supervises BaseWorkers. A transport-facing PipelineWorker tees frames onto the bus; LLMWorker/LLMContextWorker/UIWorker peers subscribe. Control moves by activate_worker (handoff); parallel work by job_group(). A normal bot is just the one-worker case.

7 · The client speaks RTVI

Browsers/phones talk to a bot over the RTVI protocol — typed JSON events for user/bot speaking, transcriptions, LLM/TTS text, metrics, and UI commands — emitted by an RTVIObserver and consumed by an RTVIProcessor (Lesson 29).

The seven ideas in one glance of code

You'll build up to this across the course — but here is the whole mental model as code, annotated with which idea each line shows:

pipeline = Pipeline([          # idea 2: processors in order
    transport.input(),         # idea 4: transport = I/O only (VAD/turns live on the aggregator)
    stt,                       # idea 3: a service (STTService) with the Settings pattern
    user_aggregator,           # builds the LLMContext (conversation memory)
    llm,                       # idea 3: LLMService streams LLMTextFrames (idea 1: frames)
    tts,                       # idea 3: TTSService -> TTSAudioRawFrames
    transport.output(),
    assistant_aggregator,
])
worker = PipelineWorker(pipeline)          # a single agent
runner = WorkerRunner()                    # idea 6: owns the bus; supervises workers
await runner.add_workers(worker)           # one worker now… many = multi-agent
await runner.run()
# idea 5: swap stt+llm+tts for one GeminiLiveLLMService to go realtime
# idea 7: add an RTVIObserver and the browser sees typed events

✅ Checkpoint

1. Which two abstractions is everything built from?

The Frame (typed data packet) and the FrameProcessor (node that handles + forwards frames). A Pipeline is just processors in order.

2. Where do VAD and turn detection get configured now?

On the LLM user aggregator via LLMUserAggregatorParams — not on the transport.

3. What makes an app "multi-agent" rather than single-agent?

More than one worker on the shared bus, supervised by one WorkerRunner. A normal bot is the one-worker case.
