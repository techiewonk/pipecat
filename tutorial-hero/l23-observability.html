Observability & metrics

⏱ 40 minLevel: intermediate

In production you need to see latency, per-service timing, token usage, and health — without touching the flow. Observers watch; metrics measure; RTVI streams it to a client.

Observer vs. processor

🧠 Why observers

A processor sits in the pipeline and can change frames; an observer sits beside it and only watches. Use observers for logging/metrics so you can't accidentally break the conversation.

Metrics

worker = PipelineWorker(pipeline, params=PipelineParams(
    enable_metrics=True, enable_usage_metrics=True))
# emits MetricsFrames: TTFB (time-to-first-byte), per-service processing time, token/char usage

The framework tracks TTFB (how fast the first response byte arrives), processing time per service, and LLM/TTS usage. Built-in observers turn these into logs; Sentry ships them to a dashboard.

Writing/using an observer

from pipecat.observers.base_observer import BaseObserver

class MyObserver(BaseObserver):
    async def on_push_frame(self, data):        # called per frame; never blocks the flow
        logger.debug(type(data.frame).__name__)

worker = PipelineWorker(pipeline, observers=[MyObserver()])
# ready-made: DebugLogObserver, LLMLogObserver, TurnTrackingObserver, UserBotLatencyObserver

Analytics & tracing services

Beyond in-process observers, Pipecat integrates analytics/tracing back-ends so you can watch production traffic on a dashboard: Sentry (errors + performance), Langfuse and other LLM-observability tools, and OpenTelemetry spans via the @traced_llm helper. These consume the same MetricsFrame data and observer stream.

# OpenTelemetry tracing is a flag on the worker + a tracing context:
worker = PipelineWorker(pipeline, params=PipelineParams(enable_metrics=True, enable_tracing=True))
# Sentry: see examples/observability/observability-sentry-metrics.py

1. Why prefer an observer over a processor for logging?
