Deployment & the CLI

⏱ 30 minLevel: intermediate

The same bot you ran locally deploys unchanged — because the bot(runner_args) contract is what production calls. Ship to Pipecat Cloud or self-host.

The deployment contract

Because the dev runner and the cloud both call bot(runner_args) and use create_transport, "works on my machine" really does mean "works in production." You choose the transport and infra; the pipeline code doesn't change.

The CLI

pipecat --help                 # scaffold, run, and deploy from the terminal
# scaffold a new project (writes AGENTS.md + CLAUDE.md), run locally, then deploy
uv run pipecat cloud deploy    # deploy to Pipecat Cloud (managed infra)

🧠 Cloud vs. self-host

Pipecat Cloud is managed infrastructure run by the Pipecat team — you push and it scales. Self-host runs the same server on your own machines (containers, your WebRTC/SIP infra). Both call the identical bot() entry point.

🔬 Source anchors

cli/ — the pipecat command (scaffold/run/deploy). runner/run.py — the bot() discovery + server. Deployment docs: deployment overview, Pipecat Cloud.

🔨 Exercise

(1) Run pipecat --help and read the subcommands. (2) Confirm your bot() matches the entry contract. (3) (Optional) scaffold a fresh project and deploy a hello-bot.

✅ Checkpoint

1. Why does a bot deploy without code changes?

Local runner and cloud both call the same bot(runner_args) entry point and select the transport via create_transport.

2. Cloud vs. self-host — same or different code?

Same code; only the infrastructure differs.
