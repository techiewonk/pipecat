Lesson 12 · Part II — The voice loop

Function calling, async tools & MCP

⏱ 50 minLevel: intermediateHigh value

Function calling turns a talker into a doer: the LLM asks to run a function, Pipecat runs your Python, and feeds the result back. MCP extends this to tools hosted in a separate server.

The call loop

Define & register a tool

from pipecat.services.llm_service import FunctionCallParams

async def get_current_weather(params: FunctionCallParams, location: str, format: str):
    """Get the current weather.
    Args:
        location: The city and state, e.g. "San Francisco, CA".
        format: "celsius" or "fahrenheit".
    """                                                    # the docstring IS the schema
    data = await fetch_weather(location, format)           # your real work
    await params.result_callback(data)                     # return to the LLM

@llm.event_handler("on_function_calls_started")            # speak while a slow tool runs
async def _(service, function_calls):
    await tts.queue_frame(TTSSpeakFrame("Let me check on that."))

context = LLMContext(tools=[get_current_weather])          # register by passing to context

🐍 The docstring is the contract

Pipecat reads the function name, typed arguments, and docstring to tell the LLM how to call it. Vague docstring = the tool never gets used. (Prefer an explicit FunctionSchema for realtime providers — see Lesson 15.)

Async & cancellable tools

By default a tool is "sync" (the LLM waits). Register with cancel_on_interruption=False to make it "async": the LLM continues, and the result is injected later as a developer message. Interruptions cancel in-flight interruptible calls.

llm.register_function("slow_lookup", slow_lookup, cancel_on_interruption=False, timeout_secs=20)
# inside slow_lookup you can stream interim updates:
await params.result_callback({"status": "still searching…"},
                             properties=FunctionCallResultProperties(is_final=False))
await params.result_callback(final_answer)   # the final result

MCP — tools from a separate server

The Model Context Protocol lets your bot use tools hosted elsewhere (memory, filesystem, a SaaS API). MCPClient discovers them and registers each as an ordinary Pipecat function.

from mcp import StdioServerParameters
from pipecat.services.mcp_service import MCPClient

mcp = MCPClient(StdioServerParameters(command="...", args=[...]))  # local subprocess
tools = await mcp.register_tools(llm)                              # its tools become the LLM's
context = LLMContext(tools=tools)
# streamable-HTTP variant points at a URL instead of a command.

✅ Checkpoint

1. Where does a tool's schema come from?

The function's name, typed parameters, and docstring (or an explicit FunctionSchema).

2. How is an MCP tool different from a local one?

It lives in a separate, standardized tool server; MCPClient registers it as a normal Pipecat function.

3. What does cancel_on_interruption=False do?

Marks the tool "async" — the LLM continues immediately and the result is injected later; the call can be cancelled on interruption.
